# Тестовое задание: Mini Stat Pipeline

## Контекст

У нас есть маленькая система из двух backend-сервисов:

- PHP-приложение хранит справочники, агрегирует статистику и показывает dashboard.
- Go-сервис принимает stat-события от внешнего JS/видеоплеера.
- PostgreSQL хранит placements, raw-события и дневные агрегаты.

Это упрощенная модель production-связки, где PHP не живет отдельно от Go-сервисов и статистического пайплайна.

## Как получить и сдать задание

2. Выполните задание локально.
3. Создайте свой репозиторий с результатом на GitHub, GitLab, Bitbucket или любом другом доступном git-хостинге.
4. Пришлите ссылку на репозиторий с решением. В вашем репозитории должны быть отражены ваши коммиты с правками, разделенные по смыслу.

Если репозиторий приватный, убедитесь, что у нас будет доступ на чтение.

## Как запустить

```bash
docker compose up -d --build
docker compose exec php php bin/console seed:demo-events
docker compose exec php php bin/console aggregate:daily 2026-08-07
open "http://127.0.0.1:18080/"
curl "http://127.0.0.1:18080/api/daily-stats?date=2026-08-07&placement_id=placement-video-main"
```

Команда `seed:demo-events` не пишет raw-события напрямую в базу. Она отправляет demo-трафик в Go-сервис `/stat`, а уже Go пишет в `raw_events`.

Полезные URL:

- Dashboard: `http://127.0.0.1:18080/`
- PHP API: `http://127.0.0.1:18080`
- Go stat endpoint: `http://127.0.0.1:17011/stat`
- Postgres: `127.0.0.1:15432`, database `stat_pipeline`, user/password `app/app`

Можно отправить событие напрямую:

```bash
curl "http://127.0.0.1:17011/stat?actionType=impression&placement=placement-video-main&price=12.34&requestId=req-1"
```

## Что нужно сделать

1. Исправить фильтр `placement_id` в API дневной статистики.

   На странице `http://127.0.0.1:18080/` есть фильтр по placement. После выбора конкретного placement таблица должна показывать только его.

   Сейчас endpoint принимает запрос вида:

   ```text
   /api/daily-stats?date=2026-08-07&placement_id=placement-video-main
   ```

   Но результат фильтруется некорректно.

2. Сделать агрегацию дневной статистики идемпотентной.

   Контекст реального проекта: агрегация сделана для того, чтобы иметь возможность перезаписать прод-статистику, изменив какие-то параметры. 
   То есть запускать агрегацию должно быть безопасно неограниченное количество раз.
   Повторный запуск команды за тот же день не должен создавать дубли или менять итоговые числа неправильно:

   ```bash
   docker compose exec php php bin/console aggregate:daily 2026-08-07
   docker compose exec php php bin/console aggregate:daily 2026-08-07
   ```

3. Проверить и исправить расчет даты агрегации.

   Бизнес-день считается в timezone из `APP_TIMEZONE`, а не в UTC.

4. Проверить прием событий в Go-сервисе.

   Нужно убедиться, что:

   - неизвестный или пустой `placement` не попадает в raw stats;
   - неизвестный `actionType` не попадает в raw stats;
   - `price=12.34` сохраняется как `1234` cents;
   - сервис возвращает понятные HTTP-коды на плохие запросы;
   - после исправления `seed:demo-events` не кладет плохие demo-события в `raw_events`.

5. Добавить минимальные проверки.

   Это могут быть unit-тесты, integration-тесты или короткий script/checklist, который можно запустить и увидеть, что баги исправлены.

6. Коротко описать в `SOLUTION.md`:

   - что было сломано;
   - как исправлено;
   - как проверялось;
   - как данные проходят путь от `seed:demo-events` или `/stat` до `/api/daily-stats`.

## Ограничения

- Не нужно добавлять Kafka, Redis, ORM, фреймворки или сложную архитектуру.
- Не нужно делать новый фронтенд, достаточно сохранить и при необходимости поправить текущую простую страницу.
- Достаточно аккуратного исправления бэкенда.
