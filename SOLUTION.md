# Решение

## Задание 1. Фильтр по placement

### Что было сломано

Причина оказалась в одной строчке. Репозиторий доставал значение фильтра из query-строки по ключу `placement`, а дашборд и контракт из README передают `placement_id`:

```php
if (!empty($query['placement'])) {          // такого ключа в запросе нет
    $where[] = 'ds.placement_id = :placement_id';
    $params['placement_id'] = $query['placement'];
}
```

Условие не выполнялось ни разу, кусок с WHERE по placement в итоговый SQL не попадал, и запрос всегда возвращал все placement за дату

### Как исправлено

```php
$placementId = trim((string) ($query['placement_id'] ?? ''));

if ($placementId !== '') {
    $where[] = 'ds.placement_id = :placement_id';
    $params['placement_id'] = $placementId;
}
```

### Как проверялось

До правки оба запроса возвращали одно и то же — это было три строки. То есть фильтр действительно ни на что не влиял.

После правки я прогнал шесть проверок. Запрос без фильтра по-прежнему отдаёт три строки. Запрос с `placement-video-main` отдаёт одну нужную. То же самое с `placement-banner-sidebar`. Запрос с пустым `placement_id=` отдаёт все три строки, не сломался. Запрос с несуществующим id отдаёт ноль строк, а не ошибку

## Задание 2. Идемпотентность агрегации

### Что было сломано

Агрегатор делал обычный INSERT, ничего не зная про уже посчитанные строки:

```php
$insert = $this->pdo->prepare(
    'INSERT INTO daily_stats (stat_date, placement_id, impressions, clicks, revenue_cents, updated_at)
     VALUES (:stat_date, :placement_id, :impressions, :clicks, :revenue_cents, now())'
);
```

Второй запуск за ту же дату не обновлял статистику, а добавлял ещё один комплект строк. Три запуска подряд дали в `daily_stats` девять строк вместо трёх, и API начал отдавать один и тот же placement по три раза, а дашборд честно утроил итоги. Помогала бага и схема: на `daily_stats` не было ограничения уникальности, база принимала сколько угодно строк на одну пару «дата плюс placement».

### Как исправлено

Миграция `002_daily_stats_unique.sql` вешает уникальный индекс на пару `(stat_date, placement_id)`, так что дубли становятся невозможны даже в обход агрегатора. Перед созданием индекса она схлопывает уже накопившиеся дубли, иначе на грязных данных он бы просто не создался.

INSERT в агрегаторе стал upsert:

```php
ON CONFLICT (stat_date, placement_id) DO UPDATE SET
    impressions = EXCLUDED.impressions,
    clicks = EXCLUDED.clicks,
    revenue_cents = EXCLUDED.revenue_cents,
    updated_at = now()
```

Одного upsert мало: он умеет добавлять и обновлять, но не удалять. Если события за день почистили и какой-то placement из них пропал, в витрине навсегда зависла бы строка со старыми числами. Поэтому после upsert команда удаляет за эту дату строки тех placement, которых больше нет в сырых событиях. Весь пересчёт обёрнут в транзакцию — день перезаписывается целиком либо не перезаписывается вообще.

### Как проверялось

На старом коде три запуска давали девять строк — зафиксировал это как исходную картину. Миграция на живой базе удалила шесть лишних строк и создала индекс.

Дальше пять запусков подряд на новом коде оставляют ровно три строки. Снимок всех чисел до и после ещё одного прогона совпал построчно, при этом `updated_at` обновился — значит строки перезаписываются, а не пропускаются.

## Задание 3. Дата агрегации в APP_TIMEZONE

### Что было сломано

Границы дня были прибиты к UTC:

```php
$start = new DateTimeImmutable($date . ' 00:00:00', new DateTimeZone('UTC'));
```

`APP_TIMEZONE` была объявлена в docker-compose, но код её вообще нигде не читался. На demo-данных это видно сразу: событие seed-3 произошло 6 августа в 21:05 UTC, то есть 7 августа в 00:05 по Москве. Московские сутки его включают, а UTC-окно выбрасывало в предыдущий день, и у `placement-video-main` за 7 августа стоял ноль показов при живом событии.

### Как исправлено

Таймзона резолвится в одном месте, `App\Timezone::app()`. На кривом значении переменной класс падает с понятным сообщением, а не откатывается молча на UTC — иначе мы получили бы ровно тот же баг, только незаметный.

В агрегаторе начало дня считается в этой таймзоне, а конец через `P1D`, а не `PT24H`. Разница вылезает в дни перевода часов: в сутках бывает 23 или 25 часов, и только `P1D` попадает в местную полночь. Для Москвы это сейчас неважно, но зашивать сюда предположение «в дне всегда 24 часа» не хочется.

Даты по умолчанию в консоли и в репозитории тоже переведены на местное время.

### Как проверялось

После правки у `placement-video-main` за 7 августа стал 1 показ вместо 0 — seed-3 вернулся в свой день. Агрегация за 6 августа собрала seed-1 и seed-2, как и должна. Сумма показов и кликов по всем дням совпала с количеством в `raw_events`, значит события не потерялись и не посчитались дважды.

Битые даты отклоняются: `2026-8-7`, `07.08.2026`, `2026-02-30`, `2026-13-01` и пустая строка дают понятную ошибку вместо тихого пересчёта не того дня. Кривая `APP_TIMEZONE` тоже падает с внятным текстом.

Отдельно отмечу, что я бы схему делал иначе. Бекенд бы полностью сидел на UTC (СУБД, приложения), сервисы отдавали данные фронтенду в том же UTC, а, к примеру, JS преобразовывал дату в локальное время пользователя. Никакой путаницы бы не возникло, восприятие кода стало бы более корректным и стандартизованным
